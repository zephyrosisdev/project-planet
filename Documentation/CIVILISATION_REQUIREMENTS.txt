We need to substantially expand the existing Unity space/RTS project into a deeper 3D planetary and interplanetary civilisation simulation.

This project already has an RTS layer based around spherical 3D planets, large numbers of units, GPU-based surface pathfinding, placeable buildings, resources, technology progression, AI factions, and a first-person mode where the player can move around physically, enter vehicles and ships, and directly control them.

Do not replace working existing systems unnecessarily. Inspect the existing architecture first and integrate with what is already there. Reuse existing unit, building, faction, resource, technology, UI, pathfinding, first-person, vehicle and ship systems wherever practical. Refactor shared functionality only where doing so significantly improves the architecture.

The main goal of this implementation is to introduce a complete interplanetary civilisation layer where both AI factions and human players can discover planets, analyse their resources, launch satellites and telescopes, establish colonies, create trade routes, supply remote colonies, exploit resources that are scarce on the homeworld, and eventually build self-sufficient multi-planetary civilisations.

The AI must use the same underlying gameplay systems as the player wherever practical. Do not simply teleport resources, magically create colonies, instantly discover planets or give the AI hidden information. The AI should construct infrastructure, manufacture spacecraft, launch missions, discover celestial bodies, establish colonies and operate logistics using the same strategic systems available to the player.

The architecture must explicitly separate large-scale strategic simulation from expensive local physical simulation.

Objects such as satellites, telescopes, freighters, colony ships and interplanetary missions should have persistent simulation-state representations even when they are nowhere near a player or active camera. They should not require active GameObjects, Rigidbody physics, rendering or per-frame MonoBehaviour updates simply to exist.

When an object becomes locally relevant, for example because a player approaches it, enters it, observes it closely, fights near it or manually takes control of it, it should be capable of being materialised into the full physical Unity representation. When it becomes irrelevant again it should be able to return to strategic simulation.

Design this cleanly around data-driven runtime state rather than thousands of permanently active Unity GameObjects.

Implement astronomy and planet discovery as an actual gameplay system.

At the beginning of the game, a faction should not automatically know every planet and every resource composition in the solar system.

The actual simulation state of the universe must be separate from each faction's knowledge of the universe.

Create something equivalent to:

UniverseState

and separately:

FactionKnowledgeBase / FactionIntelState.

The UniverseState contains the true properties of celestial bodies.

Each faction's knowledge system contains its current estimates.

A faction may:

Not know a planet exists.
Know that an unidentified body exists.
Know approximate orbit.
Know approximate size/mass.
Know atmosphere.
Have rough spectroscopy.
Know probable resource composition.
Have confirmed resource composition.
Have detailed surface survey information.

Titanium abundance 0.71.
Uranium abundance 0.22.

One faction may only know:

Iron: probably high.
Titanium: unknown.
Uranium: unknown.

Another faction may know all three accurately.

A third faction may not know the planet exists.

Maintain save/load compatibility where possible. All persistent strategic state must eventually be serialisable so the state of discovered planets, telescope observations, orbital objects, colonies, trade routes and missions can survive saving/loading.

The main end-to-end acceptance test is this:

Start an AI faction with only its home planet.

Allow it to develop without scripting the individual actions.

The AI should eventually industrialise sufficiently to determine that a strategically important resource such as titanium is becoming scarce.

It should determine that local production is inadequate.

It should search its existing astronomical knowledge.

If no suitable known planet exists, it should build appropriate astronomical infrastructure.

It should manufacture and launch an orbital telescope if necessary.

The rocket should perform a proper launch and enter stable orbit.

The telescope should perform observations.

The AI should discover another planet.

It should gather sufficient spectroscopy to suspect that the planet contains substantial titanium.

It should launch a survey probe.

The survey should confirm useful deposits.

The AI should evaluate the planet as a colonisation candidate.

It should manufacture the required colony infrastructure and transport.

It should launch a colony expedition during an appropriate transfer opportunity.

The expedition should travel to the planet and establish an outpost.

The outpost should initially depend upon imported supplies.

The AI logistics system should predict those supply requirements before shortages occur.

It should create and operate trade routes from the established industrial worlds to the colony.

The colony should construct mining and processing infrastructure.

It should begin producing titanium.

The AI should create an export route that returns titanium to the faction's main industrial economy.

The colony should gradually increase its self-sufficiency.

Eventually the colony should be capable of functioning as another strategic expansion hub.

If we run the game in omniscient observer mode, all of those decisions, routes, missions, shortages, resource flows, orbits and AI goals should be visible.

If we play as one of the factions instead, enemy information must remain hidden unless legitimately discovered by our reconnaissance/intelligence systems.

Throughout this implementation prioritise scalability, deterministic strategic simulation, clean integration with the current project, good debugging visibility, and avoiding unnecessary per-frame/GameObject overhead.

Most importantly, treat the planetary RTS, orbital simulation, interplanetary economy and first-person gameplay as different representations of the SAME persistent game world rather than separate game modes.
